AIEN Deployment Guide — VPS + Cloudflare Pages
Updated: 2026-08-29

Use this file to stand up the stack on ANY Ubuntu VPS. Replace placeholders.
Do not skip the deploy-key step. Do not mix the three keys (section 0b).

Placeholders:
  VPS_IP          e.g. 163.245.208.214
  DOMAIN          e.g. aien.store
  OWNER/REPO      e.g. your-user/aien-store-feb-14-26
  DEPLOY_USER     e.g. deploy-user
  APP_DIR         e.g. /home/deploy-user/aien-store-website
  DB_NAME         e.g. aien_store
  DB_USER         e.g. aien_user
  DB_PASS         strong password (quote it if it contains !)

Current production example (aien.store):
  api.aien.store     A -> 163.245.208.214
  www.aien.store     CNAME -> aien-store.pages.dev
  admin.aien.store   CNAME -> admin-portal-9td.pages.dev  (use YOUR Pages hostname)
  aien.store         URL Redirect 301 -> https://www.aien.store

============================================================
0) Architecture
============================================================
- api.DOMAIN     -> VPS: Nginx -> Node (127.0.0.1:3000) managed by PM2
- www.DOMAIN     -> Cloudflare Pages project "aien-store"
- admin.DOMAIN   -> Cloudflare Pages project "admin-portal"
- DOMAIN         -> redirect to https://www.DOMAIN

Workflows to use:
  .github/workflows/deploy-orchestrator.yml
  .github/workflows/deploy-backend-vps.yml
  .github/workflows/deploy-main-website-cloudflare.yml
  .github/workflows/deploy-admin-portal-cloudflare.yml

Do NOT use .github/workflows/deploy.yml for this stack (old Docker path).

Admin "Rebuild website" only runs the Cloudflare main-website workflow.
Merge to main that touches backend/** runs Deploy Backend VPS (SSH + git fetch).

============================================================
0b) Three keys — do not mix
============================================================
1) VPS login key (GitHub Actions -> VPS)
   - Private: GitHub secret VPS_SSH_KEY
   - Public:  DEPLOY_USER ~/.ssh/authorized_keys
   - Purpose: Actions can SSH in and run the deploy script

2) GitHub deploy key (VPS -> GitHub)
   - Private: DEPLOY_USER ~/.ssh/id_ed25519 on the VPS
   - Public:  GitHub repo -> Settings -> Deploy keys (read-only)
   - Purpose: git clone / git fetch origin
   - If you DELETE this on GitHub, git fetch fails with:
     git@github.com: Permission denied (publickey)
   - Fix: re-add the SAME ~/.ssh/id_ed25519.pub, or generate a new pair

3) GITHUB_DEPLOY_TOKEN (API -> GitHub API)
   - Lives in backend/.env on the VPS
   - Fine-grained PAT: this repo only; Actions Read and write; Contents Read
   - Purpose: admin Rebuild website + deploy status
   - NOT a deploy key. Recreating a deploy key does not fix token errors.

============================================================
0c) Safe order (avoid lockout)
============================================================
1. SSH as root works
2. Create DEPLOY_USER + test key login from your laptop
3. Firewall
4. Deploy key on GitHub, then clone
5. Postgres + backend .env + PM2
6. DNS A record for api, then Nginx + SSL
7. GitHub Actions secrets + test backend workflow
8. Cloudflare Pages + frontend custom domains
9. Harden SSH (disable password/root) LAST

============================================================
1) VPS base packages (Ubuntu)
============================================================
ssh root@VPS_IP

apt update && apt upgrade -y
apt install -y git curl ufw postgresql postgresql-contrib postgresql-client
curl -fsSL https://deb.nodesource.com/setup_20.x | bash -
apt install -y nodejs
npm i -g pm2

node -v    # v20.x
npm -v
psql --version
pm2 -v

============================================================
2) Deploy user
============================================================
adduser DEPLOY_USER
usermod -aG sudo DEPLOY_USER

mkdir -p /home/DEPLOY_USER/.ssh
# Copy YOUR laptop pubkey (the one you use to SSH), not the GitHub deploy key:
cp /root/.ssh/authorized_keys /home/DEPLOY_USER/.ssh/authorized_keys
chown -R DEPLOY_USER:DEPLOY_USER /home/DEPLOY_USER/.ssh
chmod 700 /home/DEPLOY_USER/.ssh
chmod 600 /home/DEPLOY_USER/.ssh/authorized_keys

Test from laptop (keep this working before later hardening):
ssh DEPLOY_USER@VPS_IP

============================================================
3) Firewall
============================================================
sudo ufw allow OpenSSH
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw enable
sudo ufw status verbose
# Expect: 22, 80, 443 allow; incoming default deny

============================================================
4) GitHub deploy key (REQUIRED before clone and before Actions git fetch)
============================================================
As DEPLOY_USER:

ssh-keygen -t ed25519 -C "vps-deploy-readonly" -f ~/.ssh/id_ed25519 -N ""
cat ~/.ssh/id_ed25519.pub

GitHub -> this repository -> Settings -> Deploy keys -> Add deploy key
  Title: vps-backend-deploy
  Key: paste the .pub line
  Allow write access: OFF

Test:
ssh -T git@github.com
# Success looks like: Hi OWNER/REPO! You've successfully authenticated...

--- Recreate after you deleted the deploy key on GitHub ---
The private key is usually still on the VPS.

ssh DEPLOY_USER@VPS_IP
cat ~/.ssh/id_ed25519.pub
# Add that exact line back as a new deploy key (read-only).

If the key files are gone:
ssh-keygen -t ed25519 -C "vps-deploy-readonly" -f ~/.ssh/id_ed25519 -N ""
cat ~/.ssh/id_ed25519.pub
# Add new .pub on GitHub. Then:
cd APP_DIR
git remote set-url origin git@github.com:OWNER/REPO.git
ssh -T git@github.com
git fetch origin

Wrong user: the key must belong to VPS_USER (DEPLOY_USER).
A key under /root/.ssh is ignored when Actions SSH as deploy-user.

============================================================
5) Clone the repo
============================================================
As DEPLOY_USER:
cd ~
git clone git@github.com:OWNER/REPO.git aien-store-website
# APP_DIR is now /home/DEPLOY_USER/aien-store-website
git -C ~/aien-store-website remote -v
# Must show git@github.com:OWNER/REPO.git (SSH, not https)

============================================================
6) Postgres
============================================================
sudo -u postgres psql

CREATE DATABASE DB_NAME;
CREATE USER DB_USER WITH ENCRYPTED PASSWORD 'DB_PASS';
GRANT ALL PRIVILEGES ON DATABASE DB_NAME TO DB_USER;
\q

sudo -u postgres psql -d DB_NAME
GRANT USAGE, CREATE ON SCHEMA public TO DB_USER;
ALTER SCHEMA public OWNER TO DB_USER;
ALTER DATABASE DB_NAME OWNER TO DB_USER;
\q

sudo systemctl enable --now postgresql

# Quote the URL if password contains !
psql 'postgresql://DB_USER:DB_PASS@127.0.0.1:5432/DB_NAME'

============================================================
7) backend/.env (API server only)
============================================================
cd ~/aien-store-website/backend
cp .env.example .env
nano .env

Required in production:

NODE_ENV=production
PORT=3000
DATABASE_URL=postgresql://DB_USER:DB_PASS@127.0.0.1:5432/DB_NAME?schema=public&options=-c%20TimeZone%3DUTC
JWT_SECRET=<long random string — not change-me-in-production>

CORS_ORIGIN=https://www.DOMAIN,https://DOMAIN,https://admin.DOMAIN
APP_URL=https://www.DOMAIN
ADMIN_URL=https://admin.DOMAIN
API_URL=https://api.DOMAIN

GITHUB_DEPLOY_TOKEN=github_pat_...
GITHUB_REPO=OWNER/REPO
GITHUB_MAIN_WEBSITE_WORKFLOW=deploy-main-website-cloudflare.yml

Also set if you use them (see backend/.env.example):
  Cloudinary or other storage
  MAIL_PROVIDER + API key
  GOOGLE_CLIENT_ID / SECRET
  SEED_ADMIN_EMAIL / SEED_ADMIN_PASSWORD / SEED_ADMIN_NAME (before first seed)

Create GITHUB_DEPLOY_TOKEN:
  GitHub -> Settings -> Developer settings -> Fine-grained tokens
  Resource owner = repo owner
  Only this repo
  Actions: Read and write
  Contents: Read
  Approve + SSO authorize if the org requires it
  Restart after changing: pm2 restart aien-backend --update-env

Do not put GITHUB_DEPLOY_TOKEN in main-website/.env or admin-portal/.env.

============================================================
8) First backend start
============================================================
cd ~/aien-store-website/backend
npm ci
npm run build
npx prisma migrate deploy
npm run db:seed
# seed once. Creates first admin from SEED_ADMIN_* 

pm2 start npm --name aien-backend -- run start:prod
pm2 save
pm2 startup
# run the command pm2 startup prints (uses sudo)

pm2 status
curl -I http://127.0.0.1:3000/health
# Expect 200

pg-boss schema is created automatically on first start.

Always run npm scripts from backend/, not repo root.

============================================================
9) DNS for API, then Nginx + TLS
============================================================
At the registrar (e.g. Namecheap), set:
  api   A     VPS_IP

Wait until:
  dig +short api.DOMAIN
shows VPS_IP.

sudo apt install -y nginx certbot python3-certbot-nginx
sudo nano /etc/nginx/sites-available/api.DOMAIN

server {
    listen 80;
    server_name api.DOMAIN;

    client_max_body_size 20m;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

sudo ln -sf /etc/nginx/sites-available/api.DOMAIN /etc/nginx/sites-enabled/
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t
sudo systemctl reload nginx

sudo certbot --nginx -d api.DOMAIN
curl -I https://api.DOMAIN/health
# GET / may be 404; /health must be 200

sudo systemctl status certbot.timer --no-pager
sudo certbot renew --dry-run

10) Remaining DNS (frontends)
============================================================
After Cloudflare Pages custom domains exist (section 12), set:

  @       URL Redirect (301)  https://www.DOMAIN
  www     CNAME               <aien-store Pages hostname, e.g. aien-store.pages.dev>
  admin   CNAME               <admin-portal Pages hostname — unique per account>
  api     A                   VPS_IP
  Keep existing TXT (Google site verification) if any

Never put both A and CNAME on the same host.

dig NS DOMAIN +short
dig +short www.DOMAIN
dig +short admin.DOMAIN
dig +short api.DOMAIN
dig @1.1.1.1 admin.DOMAIN +short

============================================================
11) GitHub Actions: VPS login key + secrets
============================================================
On your LAPTOP (separate key from the GitHub deploy key):

ssh-keygen -t ed25519 -C "github-actions-vps" -f ./gha_vps -N ""

On VPS as DEPLOY_USER:
  append gha_vps.pub to ~/.ssh/authorized_keys
  chmod 600 ~/.ssh/authorized_keys

From laptop:
  ssh -i ./gha_vps DEPLOY_USER@VPS_IP
  # must work without a password

GitHub repo -> Settings -> Secrets and variables -> Actions -> Secrets:

  VPS_HOST      VPS_IP
  VPS_PORT      22
  VPS_USER      DEPLOY_USER
  VPS_SSH_KEY   entire private file gha_vps (BEGIN/END PRIVATE KEY)
  VPS_APP_DIR   /home/DEPLOY_USER/aien-store-website
  DEPLOY_BRANCH main

Delete ./gha_vps locally after it is stored in GitHub if you do not need a local copy.

Test: Actions -> Deploy Backend VPS -> Run workflow (branch main).
Expect git fetch + npm ci + migrate + pm2 restart.

If this job fails at git fetch with Permission denied (publickey):
  that is the GitHub DEPLOY KEY (section 4), not VPS_SSH_KEY.
  SSH into the box already succeeded.

If it fails before git (timeout / Permission denied / Host key):
  fix VPS_HOST / VPS_USER / VPS_SSH_KEY / authorized_keys / firewall.

============================================================
12) Cloudflare Pages + GitHub environment CLOUDFLARE
============================================================
Dashboard -> Workers & Pages -> Create -> Pages -> Upload assets
  Project 1: aien-store
  Project 2: admin-portal

Each project -> Custom domains:
  aien-store    -> www.DOMAIN
  admin-portal  -> admin.DOMAIN
Use the exact *.pages.dev hostname Cloudflare shows in DNS CNAMEs.

API token: My Profile -> API Tokens
  Template "Edit Cloudflare Workers" or custom
  Account -> Cloudflare Pages -> Edit
Account ID: from dash.cloudflare.com/ACCOUNT_ID/...

GitHub -> Settings -> Environments -> create "CLOUDFLARE"

Environment secrets:
  CLOUDFLARE_API_TOKEN
  CLOUDFLARE_ACCOUNT_ID

Environment variables (build-time; required):
  PUBLIC_API_URL     https://api.DOMAIN
Optional:
  CLOUDFLARE_ZONE_ID   (cache purge after deploy)
  PUBLIC_SITE_URL      https://www.DOMAIN   (if you add it to the workflow later)

Without PUBLIC_API_URL on this environment, production JS may point at localhost.

17) Troubleshooting
============================================================
A) Merge to main / Deploy Backend VPS:
   git@github.com: Permission denied (publickey)
   Meaning: on the VPS, GitHub rejected the SSH key.
   Fix: section 4 (re-add or recreate deploy key). Confirm:
     whoami == VPS_USER
     git remote is SSH for OWNER/REPO
     ssh -T git@github.com works
     git fetch origin works

B) Admin: Check GITHUB_DEPLOY_TOKEN permissions (Actions: Read and write)
   Meaning: API got 401/403 from GitHub API.
   Fix: new fine-grained PAT (Actions write + Contents read), backend/.env, pm2 restart.
   Not the workflow YAML permissions block.

C) Admin rebuild works, merge backend job fails
   Expected if only the deploy key is broken. They are different keys.

D) Host key verification failed (Actions SSH)
   First connection from the runner. Add host key / fingerprint for
   appleboy/ssh-action, or ssh-keyscan from a trusted machine.

E) Prisma permission denied for schema public
   Re-run grants in section 6.

F) bash: event not found (password with !)
   Use single quotes around DATABASE_URL.

G) curl https://api.DOMAIN/ is 404
   Fine. Check /health.

H) Certbot failed
   api.DOMAIN A record must already point at this VPS.

I) Site cannot reach API / CORS
   PUBLIC_API_URL on CLOUDFLARE env + CORS_ORIGIN on backend + rebuild/restart.
