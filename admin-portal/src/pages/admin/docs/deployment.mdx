# Deployment

Both the **main website** and **admin portal** deploy separately to Cloudflare Pages via GitHub Actions. Deploys run automatically when you push changes to `main`—and only when the relevant project files change (path-based triggers).

The **backend** deploys separately (e.g. Railway, Render, or your own server). See the repository’s `backend/DEPLOY-RAILWAY.md` and `backend/README.md` for backend-specific steps.

One-click **Rebuild website** on [Site deployment](/admin/site-deployment) is triggered by the **API server**, not by Cloudflare and not by `main-website/.env`. The API calls GitHub with `GITHUB_DEPLOY_TOKEN`.

## Error: Check GITHUB_DEPLOY_TOKEN permissions (Actions: Read and write)

**What it means:** GitHub returned `401` or `403`. The token on the **API server** is missing, expired, or does not have permission to read/dispatch Actions on this repo.

This is **not** the workflow `permissions:` block in YAML. That only applies to `GITHUB_TOKEN` inside the job.

**Fix (exact steps):**

1. GitHub → **Settings** (your account, or the org that owns the repo) → **Developer settings** → **Personal access tokens** → **Fine-grained tokens** → **Generate new token**.
2. **Resource owner:** the user or org that owns this repository.
3. **Repository access:** **Only select repositories** → select this repo only.
4. **Repository permissions:**
   - **Actions:** **Read and write**
   - **Contents:** **Read**
5. Generate and copy the token (`github_pat_...`).
6. If the org requires it: wait until the token is **Approved**, then **Authorize** SSO for that org.
7. On the **API host** (VPS `backend/.env`, Railway Variables, etc.) set:

```
GITHUB_DEPLOY_TOKEN=github_pat_...
GITHUB_REPO=owner/repo
GITHUB_MAIN_WEBSITE_WORKFLOW=deploy-main-website-cloudflare.yml
```

`GITHUB_REPO` must be exactly `owner/repo` for the repo that contains `.github/workflows/deploy-main-website-cloudflare.yml`.

8. Restart the API so it picks up the new env (e.g. `pm2 restart aien-backend`). Do not put this token in `main-website/.env` or the admin portal.

**Confirm the token works** (replace `OWNER/REPO`; expect HTTP `200`):

```bash
curl -sS -o /tmp/gh-runs.json -w "%{http_code}\n" \
  -H "Authorization: Bearer $GITHUB_DEPLOY_TOKEN" \
  -H "Accept: application/vnd.github+json" \
  -H "X-GitHub-Api-Version: 2022-11-28" \
  "https://api.github.com/repos/OWNER/REPO/actions/workflows/deploy-main-website-cloudflare.yml/runs?per_page=1&branch=main"
```

- `401` — wrong or expired token.
- `403` — token cannot access this repo, Actions is not **Read and write**, org approval pending, or SSO not authorized.
- `404` — wrong `GITHUB_REPO` or workflow filename (that is a different admin error).

Classic PATs need scopes `repo` and `workflow`. Fine-grained is the intended setup.

## Backend deployment (Railway or other)

When deploying the NestJS backend:

1. **Migrations:** Run `npm run db:migrate:deploy` (or use Railway’s pre-deploy: `npx prisma migrate deploy`) so the `public` schema and app tables are up to date.
2. **pg-boss (background jobs):** No extra step. The app creates the `pgboss` schema and job tables automatically on first start. You do **not** need to run `pg-boss create` or any script on each deploy. If you have an existing DB where `pgboss` was never created, see [Background jobs setup](/admin/docs/jobs-setup) for a one-time CLI command.

## Overview

| Project        | Cloudflare Pages project | Deploys when these paths change          |
|----------------|--------------------------|------------------------------------------|
| Main website   | `aien-store`             | `main-website/**` or its workflow file   |
| Admin portal   | `admin-portal`           | `admin-portal/**` or its workflow file   |

Push to `main`, and only the projects you changed will be built and deployed.

---

## GitHub Secrets

The workflows use a GitHub **environment** called `CLOUDFLARE` with these secrets:

| Secret                  | Purpose                                                       |
|-------------------------|---------------------------------------------------------------|
| `CLOUDFLARE_API_TOKEN`  | API token with Cloudflare Pages edit permission               |
| `CLOUDFLARE_ACCOUNT_ID` | Your Cloudflare account ID (32-character hex, e.g. from the dashboard URL) |

To create an API token:

1. Cloudflare dashboard → **My Profile** → **API Tokens**
2. **Create Token** → use the “Edit Cloudflare Workers” template or create a custom token
3. Ensure **Account → Cloudflare Pages → Edit** permission is enabled

Account ID: In the dashboard URL (`https://dash.cloudflare.com/<ACCOUNT_ID>/...`) or under **Workers & Pages** → **Account details**.

---

## Cloudflare Pages Projects

Both projects must exist in Cloudflare before the first deploy:

1. Cloudflare dashboard → **Workers & Pages** → **Create application** → **Pages**
2. Choose **Upload your static files**
3. Create project `aien-store` for the main website
4. Create project `admin-portal` for the admin portal

You can upload a dummy file or leave them empty; GitHub Actions will upload the built `dist` folder on each deploy.

---

## Deployment Flow

1. Push changes to `main`
2. GitHub Actions runs only if the relevant paths changed (see table above)
3. Job installs dependencies (`npm ci`), builds (`npm run build`), then runs `wrangler pages deploy dist`
4. Cloudflare Pages serves the new build

View runs and logs under the repository **Actions** tab.

---

## Manual Deployment (Optional)

If you need to deploy from your machine:

**Main website:**

```bash
cd main-website
npm run build
npx wrangler@3 pages deploy dist --project-name=aien-store
```

**Admin portal:**

```bash
cd admin-portal
npm run build
npx wrangler@3 pages deploy dist --project-name=admin-portal
```

Log in first: `npx wrangler login`, or set `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` in your environment.

> **Note:** Use `wrangler@3` locally if you see `@cloudflare/workerd-darwin-arm64` errors with newer Wrangler versions on Apple Silicon.

---

## Summary

- Path-based deploys: only changed projects run
- Uses GitHub environment `CLOUDFLARE` and its secrets
- Cloudflare Pages projects: `aien-store`, `admin-portal`
- Deploys run on push to `main` automatically
