# Deployment

**Canonical VPS playbook (from scratch on any server):** repo file `backend-vps-deployment-guide.txt`.

This page is the operational map: what deploys where, which keys do what, and how to fix the errors we actually hit.

---

## Architecture

| Hostname | Where it runs | How it deploys |
|----------|---------------|----------------|
| `api.<domain>` | VPS (Nginx → Node on `127.0.0.1:3000`, PM2) | Merge to `main` touching `backend/**` → **Deploy Orchestrator** → **Deploy Backend VPS** (SSH + `git fetch`) |
| `www.<domain>` | Cloudflare Pages project `aien-store` | Merge touching `main-website/**`, nightly cron, or admin **Rebuild website** |
| `admin.<domain>` | Cloudflare Pages project `admin-portal` | Merge touching `admin-portal/**` |
| apex `<domain>` | DNS redirect | 301 to `https://www.<domain>` |

**Rebuild website** in admin only dispatches `deploy-main-website-cloudflare.yml`. It never SSHs to the VPS. That is why a rebuild can succeed while a merge-to-`main` backend job fails.

Ignore `.github/workflows/deploy.yml` for this stack (old Docker path). Use:

- `.github/workflows/deploy-orchestrator.yml`
- `.github/workflows/deploy-backend-vps.yml`
- `.github/workflows/deploy-main-website-cloudflare.yml`
- `.github/workflows/deploy-admin-portal-cloudflare.yml`

Railway alternative for API only: `backend/DEPLOY-RAILWAY.md`.

## Three keys (do not mix)

| Name | Direction | Lives where | Purpose |
|------|-----------|-------------|---------|
| **VPS login key** (`VPS_SSH_KEY`) | GitHub Actions → VPS | GitHub repo **Actions secrets** (private key). Public half in VPS `~/.ssh/authorized_keys` for `VPS_USER` | Lets the workflow SSH in and run deploy commands |
| **GitHub deploy key** | VPS → GitHub | VPS `~/.ssh/id_ed25519`. Public half in GitHub **Repo → Settings → Deploy keys** | Lets `git fetch` / `git clone` over `git@github.com` |
| **GITHUB_DEPLOY_TOKEN** | API server → GitHub API | VPS `backend/.env` (or Railway vars) | Admin **Rebuild website** + deploy status. Fine-grained PAT: Actions **Read and write**, Contents **Read** |

Deleting a **deploy key** on GitHub does **not** delete `GITHUB_DEPLOY_TOKEN` or `VPS_SSH_KEY`. Recreate the deploy key (below). Do not rotate the other two unless they were also deleted.

## Error: `git@github.com: Permission denied (publickey)`

**When:** Merge to `main` (or **Deploy Backend VPS**). Log shows `appleboy/ssh-action` then `git fetch` / `fatal: Could not read from remote repository`.

**What it means:** GitHub Actions **did** SSH into the VPS (`VPS_SSH_KEY` is fine). On the VPS, Git cannot read the repo. Usual cause: deploy key removed on GitHub, never added, or added for the wrong Linux user.

**Fix if you deleted the deploy key** (private key often still on the VPS):

1. SSH as **`VPS_USER`** (same as GitHub secret, often `deploy-user`):

```bash
ssh deploy-user@YOUR_VPS_IP
whoami
cd ~/aien-store-website   # or whatever VPS_APP_DIR is
git remote -v             # must be git@github.com:OWNER/REPO.git
ls -la ~/.ssh
cat ~/.ssh/id_ed25519.pub
```

2. If `.pub` exists: GitHub → this repo → **Settings** → **Deploy keys** → **Add deploy key**  
   - Title: `vps-backend-deploy`  
   - Key: the full `.pub` line  
   - Do **not** enable write access  

3. If there is no key, create one, then add the new `.pub` the same way:

```bash
ssh-keygen -t ed25519 -C "vps-deploy-readonly" -f ~/.ssh/id_ed25519 -N ""
cat ~/.ssh/id_ed25519.pub
```

4. Test, then re-run the failed Action:

```bash
ssh -T git@github.com
# expect: Hi OWNER/REPO! You've successfully authenticated...
git fetch origin
```

**If `ssh -T` works but `git fetch` fails:** `git remote -v` is HTTPS or a different repo. Set:

```bash
git remote set-url origin git@github.com:OWNER/REPO.git
```

**If you added the key as `root` but `VPS_USER` is `deploy-user`:** GitHub Actions runs as `deploy-user`. Add the key under **that** user’s `~/.ssh`.

## Error: Check GITHUB_DEPLOY_TOKEN permissions (Actions: Read and write)

**What it means:** GitHub returned `401` or `403` to the **API server**. Token missing, expired, or cannot dispatch/list Actions.

This is **not** the workflow YAML `permissions:` block (that is `GITHUB_TOKEN` inside the job).

**Fix:**

1. GitHub → **Settings** → **Developer settings** → **Fine-grained tokens** → **Generate new token**.
2. Resource owner = repo owner. Access = **this repo only**.
3. Permissions: **Actions: Read and write**, **Contents: Read**.
4. Org approval + SSO authorize if required.
5. On the **API host** only:

```
GITHUB_DEPLOY_TOKEN=github_pat_...
GITHUB_REPO=owner/repo
GITHUB_MAIN_WEBSITE_WORKFLOW=deploy-main-website-cloudflare.yml
```

6. Restart API (`pm2 restart aien-backend --update-env`). Never put this token in `main-website/.env`.

Read-only Actions is not enough (dispatch needs write). GitHub has no “dispatch only” scope.

## GitHub Actions secrets and variables

### Repo secrets (backend VPS job)

| Secret | Value |
|--------|--------|
| `VPS_HOST` | Server IPv4 |
| `VPS_PORT` | `22` unless you changed SSH |
| `VPS_USER` | Linux user that owns the clone (e.g. `deploy-user`) |
| `VPS_SSH_KEY` | **Private** key for that user (full `-----BEGIN ... PRIVATE KEY-----` block) |
| `VPS_APP_DIR` | Absolute path to the git clone, e.g. `/home/deploy-user/aien-store-website` |
| `DEPLOY_BRANCH` | `main` (fallback if the workflow input is empty) |

Create the Actions→VPS key **on your laptop** (separate from the GitHub deploy key):

```bash
ssh-keygen -t ed25519 -C "github-actions-vps" -f ./gha_vps -N ""
# Public: add ./gha_vps.pub to VPS ~/.ssh/authorized_keys for VPS_USER
# Private: paste ./gha_vps into GitHub secret VPS_SSH_KEY
```

Test: `ssh -i ./gha_vps deploy-user@VPS_HOST`. Then delete the local private file if you stored it only in GitHub.

### Environment `CLOUDFLARE` (Pages jobs)

**Secrets:** `CLOUDFLARE_API_TOKEN` (Account → Cloudflare Pages → Edit), `CLOUDFLARE_ACCOUNT_ID`.

**Variables (or secrets):** `PUBLIC_API_URL` (e.g. `https://api.aien.store`) — baked into the frontend at **build** time. `CLOUDFLARE_ZONE_ID` — only needed to purge cache.

## Cloudflare Pages

Create empty **Direct Upload** projects before the first workflow run:

1. `aien-store` — main website  
2. `admin-portal` — admin  

Custom domains: `www.<domain>` on `aien-store`, `admin.<domain>` on `admin-portal`. DNS CNAMEs point at the `*.pages.dev` hostnames Cloudflare shows (they are unique per account; do not copy an old project’s hostname blindly).

## Backend on a VPS (required steps, in order)

Do **not** harden SSH (disable password/root) until key login and Actions SSH both work.

1. Ubuntu: `git`, `curl`, `ufw`, Postgres, Node 20, `pm2`, later `nginx` + `certbot`.
2. Create `deploy-user`, copy your laptop pubkey into that user’s `authorized_keys`, log in as that user.
3. UFW: OpenSSH, 80, 443.
4. **Create the GitHub deploy key** (section above) **before** `git clone git@github.com:...`.
5. Clone into `$HOME/aien-store-website` (this path becomes `VPS_APP_DIR`).
6. Postgres: database + user; grant `USAGE, CREATE` on `public` and ownership (Prisma needs this).
7. `backend/.env` — see `backend/.env.example`. Production minimum:

```
NODE_ENV=production
PORT=3000
DATABASE_URL=postgresql://USER:PASS@127.0.0.1:5432/DB?schema=public&options=-c%20TimeZone%3DUTC
JWT_SECRET=<long random, not change-me-in-production>
CORS_ORIGIN=https://www.YOUR_DOMAIN,https://YOUR_DOMAIN,https://admin.YOUR_DOMAIN
APP_URL=https://www.YOUR_DOMAIN
ADMIN_URL=https://admin.YOUR_DOMAIN
API_URL=https://api.YOUR_DOMAIN
GITHUB_DEPLOY_TOKEN=
GITHUB_REPO=owner/repo
GITHUB_MAIN_WEBSITE_WORKFLOW=deploy-main-website-cloudflare.yml
```

Also set mail + Cloudinary (or other storage) if you use them.

8. `cd backend && npm ci && npm run build && npx prisma migrate deploy && npm run db:seed` (seed once).  
   `pm2 start npm --name aien-backend -- run start:prod && pm2 save && pm2 startup`.
9. Nginx: proxy `api.YOUR_DOMAIN` → `127.0.0.1:3000`. Certbot for that hostname. Point DNS `api` A record at the VPS **before** certbot.
10. Add GitHub secrets (table above). Run **Deploy Backend VPS** once by hand.

pg-boss tables are created on first API start. Details: [Background jobs](/admin/docs/jobs-setup).

## Frontends (env at build time)

`PUBLIC_API_URL` must be the public API. Set it as a **CLOUDFLARE** environment variable (not only a local `.env`). A Pages build with localhost will produce a broken production site.

Optional: `PUBLIC_SITE_URL` on the main website for SEO.

Manual deploy from a laptop:

```bash
cd main-website && npm run build
npx wrangler@3 pages deploy dist --project-name=aien-store

cd ../admin-portal && npm run build
npx wrangler@3 pages deploy dist --project-name=admin-portal
```

## Other failures (short)

| Symptom | Cause | Do this |
|---------|--------|---------|
| Actions fail before `git fetch` (SSH timeout / auth) | `VPS_SSH_KEY` / user / host / port | Fix repo secrets; pubkey on **that** user |
| `Host key verification failed` | First SSH from Actions | Add host key / fingerprint per `appleboy/ssh-action` docs |
| Admin rebuild 404 from GitHub | Wrong `GITHUB_REPO` or workflow filename | Match `owner/repo` and `deploy-main-website-cloudflare.yml` |
| Site talks to localhost | `PUBLIC_API_URL` missing on CLOUDFLARE env | Set var, rebuild Pages |
| Browser CORS errors | `CORS_ORIGIN` missing a frontend origin | Update `backend/.env`, `pm2 restart aien-backend --update-env` |
| Prisma `permission denied for schema public` | DB user lacks rights | Grant + ownership as in the VPS guide |
| Certbot fails | `api` DNS not pointing at this VPS yet | Fix A record, wait, retry |
